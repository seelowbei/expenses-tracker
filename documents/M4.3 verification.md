# M4.3 — Complete review inbox verification

November 18, 2026. Branch: `codex/m4-3`. Implementation and local verification are complete. PR review and staging verification remain. Scope and acceptance criteria: [M4 plan](../tasks/plan.md) and [incremental checklist](https://github.com/seelowbei/expenses-tracker/blob/4dcf258/tasks/todo.md).

## Delivered behavior

- Paginated pending receipts are independent of ledger month/category filters. Stable upload-time/ID cursors reach receipts older than the previous 50-row limit, including receipts without a transaction date. Existing upload/poll/list fields remain compatible.
- Owned receipt detail returns an associated entry ID or a bounded, independently validated partial draft. Missing required fields stay blank. Invalid stored extraction/warnings do not prevent manual review. Decimal extraction amounts convert exactly to safe minor units, without rounding or inventing a currency/category.
- Missing-entry review creates one `ai_edited` entry and completes its receipt atomically. Original extraction, warnings, usage and Drive metadata remain intact. A losing/repeated save identifies the winning entry without overwriting it; terminal receipts cannot recreate deleted entries.
- Both paths reuse the existing editor and optional receipt preview. Failed/uncertain saves retain input and reload server state before an explicit retry. A winning entry requires explicit version-guarded PATCH for further changes. Saved state refreshes every ledger scope, the inbox and Recent receipts; stale reads cannot restore pending badges.
- Inbox save resets pagination and restores keyboard focus to its heading. Account keys and late-response guards prevent another account receiving review data.

No migrations, dependencies, infrastructure/bindings, Drive writes or extraction-agent files changed. M4.4 category creation and M4.5 deletion remain out of scope. No real receipt data was used or transmitted during verification.

## Browser evidence

Chrome inspected the built SPA against a localhost-only synthetic HTTP fixture (53 pending receipts, existing/missing entries, and controllable save failures). Workerd tests above independently exercised the actual API and D1; the browser fixture is not evidence of live Google authentication or deployed behavior.

Observed:

1. Page two exposed the three oldest receipts. A missing date stayed blank and blocked submission. Filling it and saving created the expense, removed pending review, returned the inbox to page one and changed SGD totals from 12.34 to 24.68 without reloading.
2. Existing-entry confirmation used PATCH, immediately removed the pending item and updated its Recent receipts badge to Done.
3. Changing ledger month/category left all pending receipts reachable in the inbox.
4. A simulated competing save displayed the winning values, retained the draft and disabled save until an explicit choice. A simulated 500 reloaded the still-pending receipt, retained input and required “Check draft and retry” before another POST.
5. A response dropped after commit reloaded the saved entry. Choosing to retain the draft issued a version-guarded PATCH; fixture request history showed one POST and one PATCH, with no second created entry.
6. Missing Drive originals displayed a recoverable preview error while edits and saves continued.
7. At 320px in dark mode, switching between Receipt and Expense details retained date/text values. Desktop light and phone dark screenshots were inspected. Layout measurements at 320/768/1024/1440px showed no document/dialog horizontal overflow. Native keyboard entry into date controls worked.
8. Final focus-fix verification showed no dialog after saving and `document.activeElement.id === 'review-heading'`.
9. A fresh Bob view showed an empty inbox and no Alice form/data. Late account-switch/sign-out races are covered by the query-client tests.

Browser console inspection showed only the deliberately failing receipt-preview requests (404); no application exceptions or React warnings appeared in the inspected final session. Injected save-failure/response-loss scenarios naturally generated failed network requests in their sessions.

**Browser-tool limits:** Escape on a dirty form led to a native confirmation workflow that stalled automation; dismissal/acceptance was not verified in this run. The native fallback also timed out. The unchanged dirty-close protection remains in the shared editor, but its complete manual confirmation flow is a staging follow-up. Live account switching by tab refocus was not demonstrated: the test tool kept the original document visible, so it did not trigger visibility-based profile refetch. Automated cache isolation and fresh-account rendering passed; verify live switching with real accounts in staging. No automated axe audit or deployed CPU measurement was performed.
